# Dawa24 Store — Design Context

Generated by `/impeccable teach`, 31 Aug 2026. This file is the source of design truth for
every UI change. Read it before any styling, component, or layout work.

## Users

Three audiences share one platform, and they are not alike:

1. **Pharmacy staff (customers)** — the primary audience. Working a counter in Egypt,
   daytime, bright ambient light, on a **mid-range Android phone**, one-handed, and
   interrupted constantly. Often not tech-confident. The job: find a medicine, compare
   supplier prices, place an order, chase a delivery — fast, between customers.
2. **Supplier staff (vendors)** — back-office, desktop, longer sessions. Managing offers,
   inventory, warehouses, incoming orders and fulfilment.
3. **Platform staff (admin)** — desktop, **all day**. Approvals, organisations, finance,
   catalogue. Sustained table work; eye strain is a real cost.

Evening and low-light use is common across all three.

## Brand Personality

**Approachable, clear, reassuring.**

This is regulated medicine supply, so it must feel trustworthy — but the route to trust
here is *clarity*, not institutional weight. Generous spacing, plain language, one obvious
next action per screen. A pharmacist who is not confident with software should never feel
stupid using it.

Arabic-first (RTL), with English as a genuine second language, not a courtesy toggle.

## Aesthetic Direction

**Theme:** Light is the default — the primary user stands under shop lighting with a phone.
Dark is a **first-class target**, not an afterthought, because evening use is common and
admin staff stare at tables all day. Both themes get equal design effort.

**Colour:** The clinical blue stays as the brand hue, rebuilt properly in OKLCH with
neutrals tinted toward it. Refined, not replaced.

**Density:** Two modes from one component set — `comfortable` (default; pharmacy and
customer surfaces, large touch targets) and `compact` (admin and vendor tables). Density is
a token, never a fork of the components.

### Anti-references — actively avoid

**The generic AI/SaaS template.** Specifically banned:
- Purple-to-blue gradients; cyan-on-dark; neon accents
- Coloured side-stripe borders on cards, alerts, list items (`border-left: 3px solid …`)
- Gradient text (`background-clip: text`)
- Icon-in-a-rounded-square above every heading
- Everything centred; identical card grids repeating icon + heading + text
- Decorative sparklines that convey nothing
- Glassmorphism used as decoration rather than for a real depth relationship
- Oversized hero metric blocks

Also avoid: legacy Arabic ERP chrome (cramped tables, tiny type, grey gradients), and
consumer-marketplace clutter (badge spam, competing calls to action).

## Typography

Arabic-first constrains the field, and quality of the Arabic cut outranks novelty.

- **Primary — `Readex Pro`.** Designed explicitly for readability across Arabic and Latin,
  variable weight, warm without being informal. Deliberately not Cairo or Tajawal, which
  are the Arabic web's monoculture, and not the incumbent IBM Plex Sans Arabic.
- **Data — `Spline Sans Mono`.** SKUs, batch numbers, tracking codes, API keys only. Not
  used as decoration, and never as shorthand for "technical".
- Body numerals use `font-variant-numeric: tabular-nums` in every table and money column.
- Fixed `rem` type scale for the product UI (dashboards do not want fluid type). Fluid
  `clamp()` only on public marketing pages.
- Minimum 1.25 ratio between steps; five steps, not eight.
- Arabic needs slightly more line-height than Latin at the same size — set it per script.

## Design Principles

1. **The counter test.** If a pharmacist cannot complete the task one-handed, on a
   mid-range Android, in bright light, while being interrupted — it is not done.
2. **Clarity is the trust signal.** No decoration earns its place unless it makes something
   easier to understand. Reassurance comes from legibility and obvious next steps.
3. **One component, two densities.** Never fork a component for admin. Density, spacing and
   touch targets come from tokens.
4. **RTL is the default, not the adaptation.** Logical properties everywhere
   (`margin-inline`, `inset-inline-start`). A physical `left` is a latent bug.
5. **Both themes, equally.** Every token is defined for light and dark, and contrast is
   verified in both. Neither theme is the "real" one.
